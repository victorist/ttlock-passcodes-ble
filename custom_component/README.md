# ttlock_ble_passcode — кастомный компонент

Этот компонент добавляет сервисы управления PIN-кодами к интеграции `ha-ttlock-ble`.
Коды хранятся в самом замке и управляются напрямую через BLE — облако TTlock не используется.

## Установка

Скопируй папку `ttlock_ble_passcode/` в директорию `custom_components/` вашего Home Assistant:

```
/config/custom_components/ttlock_ble_passcode/
  __init__.py
  manifest.json
  services.yaml
```

После этого перезапусти Home Assistant.

## Предоставляемые сервисы

После установки станут доступны следующие сервисы (в разделе Инструменты разработчика → Сервисы):

### `ttlock_ble_passcode.add_passcode`
Добавляет PIN-код в замок через BLE.

| Параметр | Тип | Описание |
|---------|-----|----------|
| `entity_id` | entity | Замок (интеграция `ttlock_ble`, домен `lock`) |
| `passcode` | string | PIN-код (4-9 цифр) |
| `name` | string | Имя кода |
| `start_time` | string | Начало в формате `YYYY-MM-DD HH:MM` |
| `end_time` | string | Окончание в формате `YYYY-MM-DD HH:MM` |

Возвращает в `response_variable`:
```yaml
success: true
passcode: "12345"
```

### `ttlock_ble_passcode.get_passcodes`
Читает список PIN-кодов из памяти замка через BLE.

| Параметр | Тип | Описание |
|---------|-----|----------|
| `entity_id` | entity | Замок |

Возвращает:
```yaml
passcodes:
  - passcode: "12345"
    type: "period"
    start_date: "2024-01-01 00:00"
    end_date: "2024-12-31 23:59"
```

> ⚠️ Видны только Custom Passcode (записанные в память замка).
> Random Timed Passcode (алгоритмические) через BLE не видны.

### `ttlock_ble_passcode.delete_passcode`
Удаляет PIN-код из замка по значению кода.

| Параметр | Тип | Описание |
|---------|-----|----------|
| `entity_id` | entity | Замок |
| `passcode` | string | Код для удаления |

## Событийный старт: как работает ожидание окна рекламы (v1.1)

Замки TTLock большую часть времени находятся в deep sleep: радиомодуль активен
только в моменты передачи advertisement-пакетов (примерно раз в ~30 с), и
GATT-соединение возможно только внутри этого окна. Поэтому вызов сервиса,
стартовавший в случайный момент, часто падал с «Замок недоступен по BLE».

Теперь сервисы работают по семантике «положи операцию в очередь и верни
результат, когда замок появится в эфире»:

1. Вызов `add_passcode` / `get_passcodes` / `delete_passcode` ставит операцию
   в per-lock FIFO-очередь (`hass.data[DOMAIN]`). К одному замку операции
   выполняются строго последовательно, к разным — параллельно.
2. Триггер «замок в эфире» (в порядке приоритета):
   - **bluetooth-колбэк** на MAC замка — основной путь: при появлении
     advertisement-пакета взводится wake-событие очереди;
   - **сенсор «Last seen»** устройства замка (fallback, если bluetooth API
     недоступен): wake по обновлению состояния сенсора;
   - **немедленные попытки с ретраями** (если сущностей-триггеров нет).
3. Executor очереди ждёт wake-событие (если замок не «awake» по состоянию или
   диагностической сущности «Bluetooth connection»), после чего делает до
   `max_attempts_per_window` попыток с паузой `wake_retry_gap`, до истечения
   `timeout` (по умолчанию `default_timeout: 90`, можно переопределить полем
   `timeout` вызова, 10–600 с).
4. По истечении таймаута операция завершается ошибкой
   «Таймаут ожидания окна BLE-рекламы (N с) для <entity>». Скрипты менять не
   нужно — контракт сервисов не изменился.

Логи: цепочка «enqueue → wake event → attempt → success» видна при
`logger: {logs: {custom_components.ttlock_ble_passcode: debug}}` в
`configuration.yaml`.

## Требования

- Home Assistant 2024.1+
- Интеграция `ha-ttlock-ble` установлена и настроена
- Замки настроены с Admin Key (нужен для изменения PIN-кодов)
